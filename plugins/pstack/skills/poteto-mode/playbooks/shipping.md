### Shipping

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

**You own what lands. Verify each PR independently, land only the verified run from the root, one PR at a time under the user's landing authority, confirm each landing, and otherwise keep your hands off the stack.** This is the half after `playbooks/babysit.md`. Read [Merge and restack safety](../references/merge-safety.md) before merging, arming, rebasing, or retargeting.

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). On entry, inspect pending merge requests with `ship-pr inspect` and cancel any that lack the durable gates of step 4. One verifier per PR, each a background subagent in its own worktree, runs the change the way a user would through the driver skill, parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. Record each verdict's head SHA, base SHA, base branch, and stable `git patch-id` of the base-to-head diff.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. A matching patch-id may preserve substantive review after a history rewrite, but it does not prove the review applies to a different destination or changed dependencies, so check that applicability before keeping it, and always rerun current checks and mergeability after a rewrite or retarget.
4. **Land bottom-up, one PR at a time, under a service-enforced head condition.** Before any rewrite or retarget, run `ship-pr inspect` and `ship-pr cancel-pending` from the safety reference for every PR the change can affect, descendants included, and require a `cancelled` readback before any push or base edit. If cancellation fails, state is unavailable, or a PR merges meanwhile, stop and reconcile actual state first. Always merge the run's lowest unmerged PR. On GitHub, use `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`, because a last-second read without that condition leaves a race, and confirm the destination immediately before the request, because the head guard does not guard the base branch. Use `origin pr merge <pr>` only after Origin's CLI proves an equivalent server-side head condition. Never guess a flag or fall back to an unguarded merge; without a guarded path, stop at merge-ready and report the limit. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) or queue admission only behind repository rules that enforce the verdict and the required CI on the revision that will land, because it lands whatever head is ready. Never change protection settings or use `--admin` to get there; without those gates, keep watching and issue a guarded immediate merge when ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease` against the captured remote head. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>` under the installed plugin) under `/loop` in dynamic mode, with no second sleep loop, until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. The watcher owns blocker classification. Route each `BLOCKER` reason through `playbooks/babysit.md`: conflicts and `behind-base` to the topology owner, threads and CI to the PR owner, human approval gates to a wait. `WAITING`, including `merge-queue`, is non-terminal, pending checks are neither failure nor completion, and unknown state never permits a merge. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Confirm each landing, then stop at the ceiling.** `COMPLETE` is a prompt to confirm actual state, not evidence of the destination. Read the PR's merged state, final head, base branch, and merge commit, fetch the intended destination, and confirm that merge commit is in its history before advancing. If any result contradicts the verified landing, stop the chain. Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what was armed or cancelled and read back, what landed and how you confirmed it, and what the next gap needs.
